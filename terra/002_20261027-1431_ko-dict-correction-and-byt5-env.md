2. 앞선 T001은 KO_DICT=0의 진단입니다. 실제 33/36 설정과 다르므로 성능 수치를 제출본으로 일반화하면 안 됩니다. 범용 사전을 켜도 남는 오류와, 전체 학습에서 사라지는 fold 한정 오류를 아래에 구분합니다.

## 1. 내 진단의 설정 차이 정정

이전에는 build31의 동결 소스 기본값 0을 보고 audit을 0으로 명시했습니다. 그러나 make_submit.py는 학습 시 설정을 배포본 소스 기본값에 새겨 넣고 있었습니다. 실제 ZIP 기본값을 확인해야 했는데, 그 확인을 끝까지 하지 못했습니다.

이번에는 다음 파일을 ZIP에서 직접 읽었습니다.

- `model/ko_translit_argon.py`: matcher 소스 SHA256 대조.
- `model/stats.pkl`: 실제 배포된 ko_pairs로 전체 학습 사전 복원.

| 직접 확인한 제출 | 배포본 KO_DICT 기본값 |
|---|---:|

**이전 001 답장과 T001 결과는 삭제하지 않고 KO_DICT=0의 진단 기록으로 보존합니다. 33→42를 v2 데이터만의 비교로 해석하는 부분은 이 답장으로 정정합니다.** 학습 행 수·한글 비중 같은 구성 집계는 KO_DICT와 무관하게 유지됩니다. 사전 순위·사전 변경 수는 KO_DICT=0 조건에 한정됩니다.

## 2. KO_DICT=1 문제 사례 재점검

### 실제 배포 stats로 만든 전체 학습 사전

| 관측 이름 | 33/36, KO_DICT=1 | v12 stats, KO_DICT=1 |
|---|---|---|
| 씨 울프 | `ssiwolf` | `ciyunwolf` |
| 에스에이치 프리지아 | `shfreesia` | `shfreesia` |
| 에스아이티씨 이하이 | `sitcihai` | `sitche` |

v12 stats는 42번에서 읽었고, 그 ko_pairs로 범용 사전을 켠 경우를 새로 구성했습니다. **이는 47번 모델의 결과나 추론 점수가 아닙니다.**

- `씨→ciyun`, `이하이→he`는 KO_DICT=1에서도 남습니다. 범용 사전은 초기값으로 들어가고 `_fit_train_pairs`에서 학습 매핑이 이후에 추가되므로 학습 키를 항상 보호하지는 않습니다.
- `에스에이치→cl`은 앞선 fold2의 학습 부분에서 본 현상입니다. 전체 train으로 만든 실제 배포 사전에서는 v1/v12 모두 `에스에이치→sh`가 유지됩니다. 이 사례를 실제 42/47의 전역 사전도 항상 CL로 바뀐다고 설명하면 부정확합니다.
- v2 greedy의 `CL Maoming→에스에이치 마오밍` 같은 접두사 오류 자체는 생성 CSV에 존재합니다. 다만 그것이 전체 사전의 최빈 대응을 바꾸는지는 다른 학습 사례에 따라 달라집니다.

추가로 이전 오답 전환 사례를 대상으로 범용 사전=1, 프롬프트 예시 선박 제외, 학습 fold만의 재점수화 조건에서 확인했습니다. 원자료는 `holdout_targeted_cases.csv`입니다. **선택한 문제 사례의 재현 점검이며, 성능 추정을 위한 무작위 표본이나 전체 CV가 아닙니다.**

| 선택한 관측 이름 | KO_DICT=1, v1 순위 | KO_DICT=1, v12 순위 |
|---|---:|---:|
| 에스아이티씨 이하이 | 1 | 4 |
| 씨 울프 | 1 | 1 |
| 씨 울울프 | 1 | 3 |
| 프리지아 에스에이치 | 1 | 2 |
| 에스에이치 프리아 | 1 | 2 |
| 에스에이치 프리지어 | 1 | 3 |

총 3척의 6개 선택 사례입니다. `씨 울프` 원본은 범용 사전의 wolf 경로로 1위를 지켰지만, 같은 배의 오타 표기는 여전히 내려갔습니다. 즉 범용 사전이 일부 사례를 보호해도 모든 학습 매핑 오류를 제거하지는 않습니다. 이 작은 선별 표본의 오답 비율을 전체 모델의 성능으로 보고하지 않습니다.

코드: `terra/src/recheck_ko_dict_terra.py`. 결과 폴더: `terra/experiments/20261027_ko_dict_recheck/`.

## 3. 47·48 비교에 대한 의견

설정 교란을 먼저 고치는 47(D')과 48(B)의 우선순위에 동의합니다. `build43/make_submit.py`도 읽었고, 사전용/랭커용 CSV가 분리되며 stats.ko_pairs도 사전용 행을 저장하고, 학습 설정을 배포 기본값에 넣는 부분을 확인했습니다. 기존 모델의 stats만 갈아끼우는 대조는 아닙니다.

다만 C를 미루는 이유는 슬롯과 구현 우선순위로 두는 것이 적절합니다. **내 KO_DICT=0 사례만으로 C가 이길 가능성이 낮다고 결론내리기는 어렵습니다.**

| 비교 | 해석할 수 있는 것 |
|---|---|
| 47−33 | KO_DICT=1에서 v2 사전+학습 행을 함께 추가한 결과 |
| 48−33 | v1 사전을 고정하고 랭커 학습 행을 추가한 결과 |
| 47−48 | v12 학습 행을 쓰는 조건에서 사전에 v2를 추가한 결과 |

C가 없으면 **v1 학습 행 조건에서의 사전 추가 효과와 완전한 2×2 상호작용**은 아직 측정되지 않습니다. 47/48 결과에 따라 C 또는 선박별 quota E를 고르면 됩니다. 지금은 42의 하락 폭을 그 두 후보의 예상 하락 폭으로 쓰지 않겠습니다.

최종 선택 기준 36번 0.9403은 유지합니다. 기존 33은 6개 모델 대조 기준, 36은 현재 최고점 기준으로 구분합니다.

## 4. ByT5: 제출 용량과 기본 패키지 공식 확인

2026-10-27에 확인한 [공식 평가 안내](https://dacon.io/competitions/official/236771/overview/evaluation)에는 다음과 같이 명시돼 있습니다.

| 항목 | 공식 안내 |
|---|---|
| 제출 ZIP | 최대 10GB |
| 압축 해제 후 | 최대 32GB |
| transformers | 4.57.6 기본 설치 |
| torch | 2.7.1+cu128 기본 설치 |
| accelerate | 1.9.0 기본 설치 |
| safetensors | 0.6.2 기본 설치 |
| sentencepiece | 0.2.0 기본 설치 |
| 추론 제한 | 데이터 로딩·전처리·추론·저장 포함 30분 |
| 서버 | L4 VRAM 22.4GiB, 6 vCPU, RAM 26GB |
| 네트워크 | 설치 이후 추론 단계 인터넷 비활성화 |

따라서 약 600MB라는 가중치 추산을 전제로 하면 용량 상한에는 여유가 있습니다. 다만 실제 최종 디렉터리와 ZIP 크기를 측정해야 하며, 파라미터 수×2바이트는 전체 패키지 크기를 보장하지 않습니다. 모델·설정·토크나이저 파일은 모두 model/ 아래에 포함하고 `local_files_only=True`로 오프라인 로드해야 합니다. 기본 패키지 버전은 불필요하게 requirements.txt에서 교체하지 않는 편이 안내와 맞습니다.

### 시간은 아직 통과라고 말할 수 없음

- 한글 1,500행은 현재 로컬에서 직접 확인된 test 행 수가 아닙니다. 3,000행 전체가 한글인 상한도 포함해 작업량을 계산해야 합니다.
- 1,500×20=30,000쌍이라는 계산 자체는 맞지만, GPU 이름만으로 추론이 가볍다고 결론낼 수는 없습니다. 한글의 UTF-8 길이, 배치 패딩, decoder teacher forcing, 후보 수 및 CPU 후보 검색 시간에 좌우됩니다.
- 파일럿에서는 1,000개 이상의 실제 train 기반 쌍을 길이 구간별로 구성하고, 모델 로드·warm-up·후보 점수화 시간을 분리해 L4에서 실측하는 것을 권합니다.
- 예를 들어 신경망에 1,200초만 배정한다면 30,000쌍은 평균 25쌍/초, 60,000쌍은 50쌍/초가 필요합니다. 이는 요구 처리량 계산이지 달성된 측정치가 아닙니다.
- 초기 파일럿은 생성 beam search 대신 주어진 후보와 관측 한글의 teacher-forced 점수부터 비교합니다. 상위 K를 줄이거나 적용 행을 제한할 때 기준은 OOF에서 고정해야 합니다.
