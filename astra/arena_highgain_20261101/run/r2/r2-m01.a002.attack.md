ATTACK 1 [MAJOR] 범위 밖 조기 반환은 잘못된 voter ID를 공식 예측으로 통과시킨다
Where: `scratch/a001/neural_challenge.py::challenge`의 english/protected110/router_locked_en_hs 조기 반환, catalog ID 검사가 뒤의 `shortlist()` 안에만 있음. 답변의 “잘못된catalogID … 중단” 및 “원본영어·보호행 변경0” 검증 설명.
Problem: 세 voter가 비어 있지 않은 문자열인지만 route에서 검사하므로, 범위 밖 행에서는 official catalog에 없는 ID를 정상 baseline/prediction으로 반환한다. 제공 TestChallenge fixture로 재현했다. (1) vessel_name='Alpha', en='NO_SUCH_CATALOG_VESSEL' → reason='english', prediction=그 미등록ID. (2) gap110=4, en=동일 미등록ID → reason='protected110', prediction=미등록ID. (3) gap110=1, en=hs=동일 미등록ID → reason='router_locked_en_hs', prediction=미등록ID. run_gpu도 전체 voter catalog 검사를 별도로 수행하지 않으므로 이러한 enriched packet은 완료 결과로 저장될 수 있다. 부모 join이 정확하다는 계약은 적혀 있지만, 실제 실행기의 fail-closed 검증과 현재 “unknown voter abort” 테스트는 scope 안만 덮는다. scope 판단 전 세 voter 전부 공식 ID인지 검증해야 한다. 보호행의 무변경이라는 이유가 잘못된 ID를 합법화하지는 않는다.

ATTACK 2 [MINOR] 모델 로드 단계 실패에는 약속한 ABORTED 반환물이 남지 않는다
Where: `scratch/a001/run_gpu.py`의 `ViewScorer(...)` 생성 loop가 `status` 생성·manifest 기록·`try/except/finally`보다 앞에 있음. 답변은 “중단 결과는 .partial과 ABORTED상태로 남김”, 준비/모델로드를 포함한 중단 조건과 반환물을 명시한다.
Problem: 실제 CUDA OOM은 scorer forward뿐 아니라 두 동결 모델을 GPU에 올릴 때 발생할 수 있다. 실제 baseline spec/src hash 검사를 사용하고 ViewScorer 생성자만 `RuntimeError('CUDA out of memory during frozen ViewScorer load')`로 대체해 main을 실행했다. nonzero 예외는 전파되지만 status.json도 partial도 생성되지 않았다. source 검증·잘못된 packet·CUDA 부재도 같은 보호구간 밖이다. 실패를 정상 후보로 쓰는 버그는 아니지만, 약속한 복귀 상태·실패 단계·소요시간을 제공하지 못해 실제 GPU handoff에서 원인 구별이 빠진다. output 경로를 확보한 뒤 준비/검증/모델로드까지 포함하는 바깥 try/finally에서 ABORTED manifest를 남기고, partial은 아직 없는 상태를 명시해야 한다.
