ATTACK 1 [MAJOR] 별도 진단기가 같은 sample_id의 이전 실행 결과를 현재 입력의 회복으로 집계한다
Where: `diagnose.py::main`, `p={r['sample_id']:r ...}`, `pred={r['sample_id']:r ...}`, `if set(p)!=set(pred)...`, 이후 `before=z['baseline']==y; after=z['candidate']==y`. 답변의 “원본 ZIP·입력·catalog 고정”, “labels는 이 단계에만 들어갑니다”, “먼저 state=COMPLETE ... 확인”.
Problem: 입력·결과를 ID집합만으로 연결한다. 결과의 status/packets_sha256를 읽지 않고, baseline이 해당 packet의 현재 router 출력인지, candidate가 scope를 지키는지조차 검증하지 않는다. 제공된 fixture/Scores로 원래 gap=.3 결과(C000→C064)를 만든 뒤 packet의 gap만4로 바꾸고 같은 결과·truth=C064를 diagnose.main에 넣었다. 실제 run_one은 보호행이므로 C001을 유지하지만 진단은 `rescue=1,candidate_correct=1,changed=1,scope_error_ceiling=0`을 정상 출력했다. 파일 I/O를 메모리 Path로 대체해 실제 diagnose.main 제어흐름을 실행한 재현이며, GPU 수치가 아니다. 같은 ID의 이전 실행파일을 잘못 연결하는 현실적인 결합 실수가 보호행 회복으로 둔갑한다. ABORT가 마지막 subset replay에서 발생한 경우에도 전체행이 담긴 partial을 직접 주면 COMPLETE 검증 없이 같은 집계가 가능하다. 또한 packet/result 중복행은 dict comprehension에서 조용히 사라지는 것도 재현했다. 고정 입력의 paired experiment라는 요구를 충족하려면 COMPLETE status와 input/packet/result hash 결합, 중복 거부, baseline router 및 scope 일치 검사가 필요하다.

ATTACK 2 [MAJOR] 점수화가 없는 실행에서는 추가시간 예산을 넘겨도 COMPLETE로 확정한다
Where: `run_gpu.py::main`의 모델 로드 이후 루프와 `status.update(state='COMPLETE'...)`; 시간 검사 위치는 `BudgetScorer.score`의 batch 전후뿐이다. 답변의 “추가 작업600초 기본·최대900초”, “초과하면 부분 결과를 후보 예측으로 쓰지 않는다”.
Problem: 대상이0행이거나 모든행이 protected/fixed_majority/insufficient_candidates라 scorer가 호출되지 않으면 deadline 검사가 한 번도 실행되지 않는다. 실제 main을 메모리 Path·mock torch/ViewScorer와 고정 clock으로 실행했다: 제공 fixture의 gap=4, budget_seconds=600, 모델 로드 후 monotonic=601로 설정하자 `state=COMPLETE,seconds=601.0,eligible_rows=0`과 partial.rename이 반환됐다. GPU측정이 아니라 실행기 경계조건 재현이다. 마지막 score 이후 긴 보호행 처리·JSON쓰기·replay가 예산을 넘기는 경우에도 최종 deadline 검사가 없다. 부모의 전체1800초 watchdog은 별도600/900초 상한을 집행하지 않으므로 이 결함을 대신 해결하지 않는다. 모델로드 후/각행 전/COMPLETE 확정 직전 전체 elapsed를 검사하고 초과시 ABORT해야 명시한 시간 계약이 성립한다.

ATTACK 3 [MINOR] 분해된 한글 입력의 추론 범위와 진단 상한이 서로 다르다
Where: `neural_rescue.py::hangul`은 `unicodedata.normalize('NFC', ...)`를 사용하지만 `diagnose.py`의 `eligible=any('\uac00'<=c<='\ud7a3' for c in x['row']['vessel_name']) ...`는 정규화하지 않는다.
Problem: 제공 fixture의 '스타 오션'을 `unicodedata.normalize('NFD', name)`로 바꾸면 run_one은 정상 한글대상으로 판단해 C000→C064를 변경하지만 진단 eligible은False가 된다. 실제 fixture/Scores 실행에서 `inference_scope=True, diagnostic_scope=False, changed=True`를 재현했다. 이는 Unicode표현만 다른 동일입력이며 원본 C_vote 최상위 라우터도 NFC를 사용한다. 그 결과 해당행의 scope_error_ceiling/pool_error_ceiling이0인데 rescue가1인 모순된 조건부 상한을 보고한다. 과제의 scope/order 검사와 오류범위 상한을 일치시키려면 진단도 nr.hangul 또는 동일한정규화 함수를 써야 한다.
